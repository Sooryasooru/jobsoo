# Database

PostgreSQL 16, accessed via SQLAlchemy 2.x and managed with Alembic.

## Tables (Phase 1)

| Table                | Purpose |
|----------------------|---------|
| `users`              | Application users (auth deferred; email unique). |
| `user_profiles`      | Candidate profile: skills, experience, education, certifications, projects, preferences. JSONB annexes for heterogeneous candidate data. |
| `resumes`            | **Original uploaded CVs only** (`kind='original'` enforced by check). Immutable: uploads never overwrite existing rows. |
| `tailored_resumes`   | Generated CV versions, one per (resume, job, version), with `approval_status` (`draft`/`pending_review`/`approved`/`rejected`) and `final_pdf_path` (NULL unless `approved`). |
| `jobs`               | Normalized listings from any source. Dedup keys: unique `(source, source_job_id)` and unique `canonical_url`. Availability (`is_active`, `is_expired`) tracked here, separate from application status. Job availability is updated by ingestion reconciliation. |
| `job_requirements`   | Structured requirements extracted via LLM + validated by Pydantic. Unique `(job_id, category, text)`. Optional fields stay NULL — never invented. |
| `job_matches`        | Per-user deterministic scores with JSONB components, matched/missing/unknown skills, evidence details, hard-blocker warnings, experience gap, and `scoring_rules_version`. Unique `(user_id, job_id)`. |
| `applications`       | Phase-1-schema tracking records. Unique `(user_id, job_id, attempt_no)`; Phase 1 uses `attempt_no=1` only (at most one per user/job), while leaving room for Phase 2 multiple attempts without a migration. |
| `application_events` | Append-only audit events for applications. |

## Conventions

- UUID primary keys (`uuid`, Python-generated via `uuid.uuid4`).
- `created_at`/`updated_at` server timestamps (`timestamptz`).
- Status/category columns are constrained text (not native enums) so adding values needs no `ALTER TYPE`.
- Foreign keys cascade on delete from parent to child (jobs → requirements, users → profiles, applications → events).
- Trigram (GIN) indexes on `jobs.title` / `jobs.company` need the `pg_trgm` extension; the initial migration creates it.

## Deviations from the approved nine-table list

None: all nine tables exist as specified. `application_events` is schema-only
until Phase 2 (no event writes outside Phase 1 tests).

## Managing migrations

```bash
cd backend
alembic revision --autogenerate -m "describe change"
alembic upgrade head        # apply
alembic downgrade -1        # revert previous migration
alembic history             # list migrations
```

Autogenerated migrations must be reviewed before committing; the
`pg_trgm` extension creation in the initial migration is one example of
adjusting autogenerated output.
